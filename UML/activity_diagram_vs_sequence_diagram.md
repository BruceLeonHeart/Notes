# 活动图是流程图吗？以及它与序列图的区别

> 类型：concept
> 一句话：活动图 vs 序列图


## 1. 活动图是流程图吗？

简单理解：是。

活动图（Activity Diagram）可以看作传统流程图（Flowchart）在 UML 中的"官方版本"或"升级版"。两者核心目的相同：描述一个过程或操作中的工作流程和步骤顺序。

### 相似之处

- 都有一个起点和终点。
- 都使用矩形（或圆角矩形）表示一个活动或动作。
- 都使用菱形表示一个判断或决策点。
- 都使用箭头表示控制流的方向。

### 活动图的增强之处

- **并发处理**：活动图有"分叉（Fork）"和"汇合（Join）"节点，可以清晰地表示并行执行的活动，这是传统流程图难以表达的。
- **对象流**：活动图不仅可以显示控制流，还可以显示"对象流"，即在活动之间传递的数据或对象。
- **泳道（Swimlane）**：可以将活动按照负责执行的参与者（如不同的类、组件或部门）进行分组，清晰地展示职责划分。

结论：如果熟悉流程图，就已掌握活动图 80% 的核心思想；活动图可视为一个功能更强大、语法更严谨的流程图。

## 2. 活动图与序列图的区别

这是两者最关键的区别，它们从完全不同的视角来描述系统。对比如下：

| 特性 | 活动图 (Activity Diagram) | 序列图 (Sequence Diagram) |
| --- | --- | --- |
| 核心焦点 | 流程和控制流 (What happens next?) | 对象间的交互和消息 (Who talks to whom?) |
| 描述对象 | 一个业务流程、一个用例的实现、或一个复杂方法的内部逻辑。 | 多个对象为了完成一个功能而进行的协作过程。 |
| 主要元素 | 活动、动作、决策点、分叉/汇合、对象流、泳道。 | 对象生命线、激活条、消息（同步/异步调用、返回）。 |
| 时间表示 | 隐式表示。只关心活动的先后顺序，不关心具体时间。 | 显式表示。时间从上到下垂直流动，清晰展示消息的先后顺序。 |
| 解决的问题 | "完成 getOdometry_3pt 这个计算需要哪些步骤？" | "当调用 getOdometry 时，OdometryXy 对象是如何与 OdomProvider、mOdom 等其他对象交互的？" |

### 一个生动的比喻

- **活动图像一份菜谱**：告诉你做一道菜的步骤（先洗菜，再切菜，然后下锅炒……），可能在某个步骤做个决定（加不加辣？），甚至可以同时做两件事（一边炖汤一边炒菜）。它关注的是"做什么"。
- **序列图像一出戏剧的脚本**：告诉你哪个演员（对象）在什么时候对另一个演员（对象）说了什么台词（消息）。它关注的是"谁和谁在对话"。

### 结合工程代码举例

对于 `odometryxy.cpp` 中的 `getOdometry` 方法：

**活动图**会描绘这个函数内部的逻辑：

1. 开始。
2. `switch (getOdomPrcType())` 是一个决策点。
3. 根据不同的 case（如 `ODOM_PRC_INT_XY_3PT_WR`），进入不同的处理分支。
4. 在某个分支里，可能会调用 `getOdometry_3pt`，然后调用 `checkOdomOut`。
5. 最后返回结果并结束。

这个图完全在 `OdometryXy` 类的内部，描述的是算法流程。

**序列图**会描绘外部如何与 `OdometryXy` 以及它依赖的对象进行交互：

1. 一个外部的 `Application` 对象向 `OdometryXy` 对象发送 `getOdometry(...)` 消息。
2. `OdometryXy` 对象的生命线被激活，它内部可能会向 `OdomProvider` 对象发送 `getSignals(...)` 消息。
3. `OdomProvider` 返回结果给 `OdometryXy`。
4. `OdometryXy` 再向 `m_modom` 对象发送 `update(...)` 消息。
5. `m_modom` 返回 `ODM_out` 结果。
6. 最后 `OdometryXy` 将结果返回给 `Application`。

这个图展示了 `Application`、`OdometryXy`、`OdomProvider`、`m_modom` 等多个对象之间的协作关系。

## 坑

- **不要用活动图画对象调用顺序**：活动图关注"做什么步骤"，对象间的消息编号/返回值/同步阻塞关系它表达不了；跨对象的调用链一律用序列图。
- **不要用序列图画单函数内部分支**：序列图的生命线是对象，if-else/循环这些控制结构在序列图里要靠片段（alt/loop）硬凑，可读性远不如活动图；一个函数内部的算法流程用活动图。
- **活动图的分叉（fork）不是"同时执行"那么简单**：它表达并行流，但没有同步原语（互斥、信号量），落到代码里要自己映射到线程/任务/协程，别误以为图里画了 fork 代码就自动并发。
- **序列图的激活条宽度没有语义**：竖条只表示对象在处理调用，不表示耗时长度；想表达异步消息要画虚线箭头，同步调用是实心箭头，混用会让读的人误解调用关系。
