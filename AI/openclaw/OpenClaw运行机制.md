# OpenClaw运行机制
**QQ/钉钉/企业微信这些机器人插件（channel），不是独立客户端连远程OpenClaw服务端，而是内置在本地Gateway网关内部的适配器；用户在IM发消息 → 插件转成统一事件交给本地Gateway → Gateway拥有本机文件/工具权限，**委托执行**文件读取、Shell、LLM调用；配对码是用来校验「哪些IM用户有权限让Gateway替他执行操作」。**

下文分架构、委托执行、配对码三层展开。

## 一、整体架构：谁是服务端，谁是机器人？
OpenClaw 只有一个核心服务：**Gateway网关（本地主进程，端口18789）**，它是唯一拥有本机权限（读文件、运行工具、调用AI）的主体，即通常所说的“服务端”。
日志中常见的 `qqbot/ddingtalk/wecom` 全部是**Channel渠道插件**，不是独立客户端，是Gateway启动时加载到进程内部的适配器模块。

数据流完整链路（以QQ机器人举例）：
1. 你在QQ私聊发消息给QQ机器人账号；
2. QQ平台服务器通过WebSocket长连接，把消息推送到你本地运行的 `qqbot` 插件；
3. `qqbot` 插件做两件事：
   - 把QQ平台私有格式消息，翻译成Gateway统一标准事件；
   - 把事件丢给本地Gateway网关处理；
4. Gateway拿到事件后，先走安全校验（配对白名单、插件允许列表、会话隔离）；
5. 校验通过 → Gateway以本机权限**代为执行**：读取本地文件、调用工具、跑AI、执行命令；
6. AI生成回复指令 → Gateway回传给 `qqbot` 插件 → 插件调用QQ API发回给用户。

### 关键区分：并非“客户端连服务端”
1. **没有远程客户端**：机器人插件和Gateway同进程本地运行，不存在跨网络连接；
2. **权限所有者永远是Gateway**：QQ/钉钉插件只有收发消息的能力，**没有读写本地文件、执行系统命令的权限**，所有高危操作必须委托Gateway完成；
3. 插件只是“翻译官+消息收发器”，真正能操作主机、调用工具的只有Gateway。

## 二、什么叫「委托执行操作」？
### 1. 委托的本质
IM渠道（QQ/钉钉）只是对外入口，平台侧的机器人账号**不能直接操作你的服务器/电脑**。
所有文件读写、脚本运行、查询本地配置、调用本地大模型，全部由**本地Gateway代理执行**，等于：
> 用户通过QQ发指令 → 授权校验通过后，Gateway受该用户委托，以本机系统权限执行任务。

### 2. 为什么安全声明反复强调“共享委托权威”
默认无用户隔离时：
A在QQ私聊发指令让Gateway读取 `/root` 密钥文件；
B在钉钉私聊发指令让Gateway删除本地日志；
两人共用同一套Gateway本机权限，**A可以委托Gateway偷看B相关数据，B也能操作A的内容**，这就是文档说的「共享委托工具权威」。

### 3. 配对码（Pairing code）和委托的绑定关系
配对码就是**委托授权凭证**，对应开头那句标语：
> Pairing codes exist because even bots believe in consent（配对码存在是因为机器人也需要授权同意）

完整配对授权流程：
1. 陌生用户第一次私聊机器人；
2. 插件拦截消息，不交给Gateway执行，自动返回8位配对码；
3. 你在服务器命令行执行 `openclaw pairing approve 渠道 配对码`；
4. Gateway把该用户ID加入 `allowFrom` 白名单；
5. 此后该用户的消息，才允许委托Gateway执行文件、工具操作；
6. 未配对用户的指令会直接丢弃，永远无法触发委托执行，保护本机安全。

## 三、两条日志警告对应这套委托安全机制
### 1. `plugins.allow is empty`
`plugins.allow` 是**插件白名单**：规定哪些渠道插件有权限向Gateway提交委托任务。
空列表 = 信任全部插件（qqbot/钉钉/企微全都能随便提交执行请求），风险是恶意插件、漏洞插件可随意委托Gateway操作主机；
解决方案：显式填入插件ID，只放行你信任的渠道。

### 2. 安全声明：默认是单人信任边界
Gateway默认设计逻辑：**本机操作员完全可信，外部IM用户默认不可信**。
- 单人自用：只有你自己配对，委托边界干净；
- 多渠道/多人共用：不配置配对白名单、会话隔离、沙盒，所有IM用户共享Gateway委托权限，极易提示注入、越权读取文件。

## 四、要点总结
1. 机器人（QQ/钉钉插件）**不是客户端**，是Gateway内部的消息适配器；
2. Gateway是唯一“服务端”，持有本机全部文件/工具权限，**所有操作都由Gateway代为委托执行**；
3. 配对码是控制「哪些外部IM用户能获得委托执行资格」的安全闸门；
4. 多机器人渠道同时加载、不配置白名单+配对校验 = 所有渠道用户共享一套本机操作权限，存在严重越权风险。

## 补充：委托权限隔离（加固方案）
1. 配置 `plugins.allow` 限定可信渠道插件；
2. 渠道开启 `dmPolicy: pairing`，陌生人必须审批配对才能委托执行；
3. `session.dmScope: per-channel-peer` 会话隔离，不同用户委托环境互不互通；
4. 工具沙盒+最小权限，限制Gateway可执行的系统操作范围。
