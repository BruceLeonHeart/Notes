RPC 只是一种“像调用本地函数一样调用远程程序”的交互模型，它对底层的传输通道没有任何强制绑定。**HTTP 只是众多可选传输载体中的一种**（之所以容易产生这种错觉，主要是因为当今最流行的 gRPC 默认选择了 HTTP/2 作为底层管道）。

在真实的软件工程中，大量 RPC 框架根本不走 HTTP，而是直接运行在以下通道之上：

---

### 1. 纯裸 TCP 协议（传统且极致性能的网络方式）

很多追求极致吞吐量的 RPC 框架会直接基于操作系统的 TCP Socket 自定义极简的私有二进制协议（例如：协议头只用 4 个字节标明后续数据包的长度，紧接着就是纯二进制数据），彻底省去 HTTP 繁琐的协议头与状态码开销。

* **典型代表**：阿里开源的 **Apache Dubbo**、**Apache Thrift**（原生 TSocket 模式），以及绝大多数大型多人在线游戏（MMO）服务器之间的底层通信。

### 2. 本地 IPC 管道（完全脱离网络与 HTTP）

当调用方和被调用方运行在同一台物理机上时，RPC 可以直接跑在操作系统的本地进程间通信通道上，连网卡和 TCP/IP 协议栈都不经过。

* **典型代表**：
* **标准输入输出（`stdio`）**：VS Code 的代码补全引擎（LSP）以及 AI 大模型的工具调用协议（MCP），最常见的做法就是主程序拉起一个子进程，双方直接通过 `stdin / stdout` 管道一行一行地收发 **JSON-RPC** 报文。
* **Unix Domain Socket**：gRPC 也可以直接配置跑在本地 Unix 套接字上，完全绕过 HTTP 网络栈。



### 3. WebSocket（全双工长连接）

当需要客户端与服务端保持持久连接、并随时双向推送指令时，RPC 常直接运行在 WebSocket 协议之上。

* **典型代表**：以太坊（Ethereum）等区块链节点普遍提供的 `ws://` 订阅接口，底层就是 **JSON-RPC over WebSocket**。

### 4. UDP / QUIC（极致低延迟场景）

在快节奏竞技游戏、工业实时控制或音视频信令同步中，TCP 的“丢包重传阻塞”会导致画面瞬时卡顿。这类场景下，开发者会基于 **UDP** 或 **QUIC**（HTTP/3 的底层传输协议）编写自定义的轻量级 RPC。

---

### 既然裸 TCP 更快，为什么 gRPC 偏偏选择 HTTP/2？

Google 在设计 gRPC 时没有自创私有 TCP 协议，而是坚定地将其建立在 HTTP/2 之上，主要是出于**基础设施兼容性**的考量：

1. **穿透防火墙与网关**：企业内网防火墙、云厂商的负载均衡器（ALB/NLB）以及反向代理（Nginx、Envoy）默认都放行并原生支持 HTTP 流量；如果是私有 TCP 协议，往往需要额外配置甚至重写网关转发插件。
2. **复用现成生态**：直接依托 HTTP/2，gRPC 可以无缝复用现有的 TLS 证书加密、链路追踪（Tracing）、身份鉴权（Header Token）以及连接多路复用机制，无需在全网基础设施上重复造轮子。
