# HTTP 与 TCP / UDP 的关系

> 类型：concept
> 一句话：HTTP/1.1 和 H2 跑在 TCP 上，HTTP/3 跑在 UDP（QUIC）上

> 注：本篇内容已并入 `RPC_intro.md`，保留原文备查。

在计算机网络的分层架构（TCP/IP 模型）中，**TCP 和 UDP 位于“传输层”，而 HTTP 位于它们之上的“应用层”**。

如果把网络通信比作寄快递：**TCP 和 UDP 是底层的“物流运输方式”（决定包裹怎么运、丢了管不管），而 HTTP 是“信纸上的书写格式”（决定双方怎么打招呼、内容怎么排版）。**

```text
应用层 (Application Layer)  ──►  [ HTTP/1.1 ]   [ HTTP/2 ]        [ HTTP/3 ]
                                      │             │                 │
                                      └──────┬──────┘                 ▼
                                             │                    [ QUIC ] (内置加密与重传)
                                             ▼                        │
传输层 (Transport Layer)    ──►         [   TCP   ]              [   UDP   ]
                                             │                        │
网络层 (Network Layer)      ──►         [            IP 协议            ]

```

---

### 1. 传输层的两大基石：TCP 与 UDP

操作系统内核直接提供了 TCP 和 UDP 两种传输管道供上层应用选择，两者的设计哲学截然相反：

| 对比维度 | TCP（传输控制协议） | UDP（用户数据报协议） |
| --- | --- | --- |
| **连接特性** | **面向连接**<br>

<br>收发数据前必须先经历“三次握手”建立连接，结束时“四次挥手”断开 | **无连接**<br>

<br>知道对方的 IP 和端口直接把数据包扔出去，不建立连接 |
| **可靠性** | **绝对可靠**<br>

<br>内置确认应答（ACK）、超时重传、数据校验，保证字节流**不丢、不重、按顺序**到达 | **尽力而为（不可靠）**<br>

<br>发出去就不管了，网络拥堵时可能丢包，到达顺序也可能乱序 |
| **传输速度与开销** | **较慢、开销大**<br>

<br>首部至少 20 字节，受限于流量控制与拥塞控制机制（遇到丢包会主动降速） | **极快、开销极小**<br>

<br>首部仅 8 字节，没有握手延迟，也没有重传阻塞 |
| **典型适用场景** | 网页浏览、文件下载、邮件收发、数据库同步（不能容忍数据残缺） | 视频通话、在线游戏、直播流、DNS 查询（宁可画面花一帧，也不能卡顿等重传） |

### 2. HTTP 与它们的历史演进关系

HTTP 协议自诞生以来，经历了从“死守 TCP”到“转向 UDP”的重大架构变迁：

#### ① HTTP/1.1 与 HTTP/2：完全建立在 TCP 之上

早期设计 HTTP 时，网页传输要求 HTML、CSS 和图片必须完整、准确地送达浏览器。直接把 HTTP 架构在 **TCP** 之上是最省心的选择——HTTP 无需自己操心网络丢包和乱序问题，全部交给操作系统的 TCP 协议栈兜底。

#### ② 为什么 HTTP/3 抛弃了 TCP，转而拥抱 UDP？

随着移动互联网普及，TCP 在高并发与弱网环境下的三大先天缺陷成了性能瓶颈：

* **TCP 队头阻塞（Head-of-Line Blocking）**：HTTP/2 虽然允许在一条 TCP 连接上并发传输多个请求，但底层 TCP 依然是单条有序字节流。只要网络中**丢失了 1 个数据包**，后面所有已经到达的数据包都必须死等这 1 个包重传成功，才能交给上层 HTTP，导致整个连接瞬间卡死。
* **握手延迟过高**：建立一次加密的 HTTPS 连接，需要先进行 TCP 三次握手，再进行 TLS 加密握手，来回需要好几个网络往返（RTT）才能开始发业务数据。
* **连接迁移困难**：手机从 Wi-Fi 切换到 5G 网络时，IP 地址发生改变，原有的 TCP 连接必须彻底断开并重新经历全套握手。

为了根治这些问题，**HTTP/3 底层彻底放弃了 TCP，改用基于 UDP 的 QUIC 协议**：

* **在用户态重造轮子**：QUIC 利用 UDP“无连接、不受内核 TCP 限制”的自由度，在应用层自己实现了一套更现代的丢包重传和加密机制。
* **独立流控**：一条 QUIC 连接内部的多条数据流完全独立。A 流丢了包，只有 A 流等重传，B 流和 C 流的数据照常处理，彻底消灭了队头阻塞。
* **极速建连与无缝切换**：将传输握手与 TLS 1.3 加密握手合并（最快 0-RTT 发送数据），且用随机生成的“连接 ID”代替 IP 地址标识连接，Wi-Fi 切 5G 时实现无感平滑过渡。

在现代网络工程中，**HTTP/1.1 和 HTTP/2 跑在 TCP 上，而现代的 HTTP/3 跑在 UDP（QUIC）上**，浏览器与服务器在建连时会自动协商并无缝切换。

### 3.HTTP3
**目前最新的官方正式大版本就是 HTTP/3**（由 IETF 于 2022 年正式发布为 RFC 9114），截至目前尚未有 HTTP/4 的计划，标准组织当前的重心是在 HTTP/3 之上扩展新特性（如 WebTransport、新的 `QUERY` 请求方法等）。

在实际工程中，网站并非“只能死选某一个版本”，而是通过**多版本共存 + 自动协商降级**的机制来运作的。

---

#### 1. 网站是如何“选择”并切换 HTTP 版本的？

开发者（或云厂商 CDN）通常不会在代码层手动写死用哪个 HTTP 版本，而是在接入层（如 Nginx、Envoy、Cloudflare 或阿里云/腾讯云 CDN）开启多版本支持，让浏览器和服务器自动“谈判”：

1. **首次建连（ALPN 协商）**：浏览器访问网站时，先通过传统的 TCP + TLS 握手，利用 TLS 的 **ALPN** 扩展与服务器协商，通常默认先建立 **HTTP/2** 连接。
2. **服务器“打广告”（`Alt-Svc` 响应头）**：如果服务器支持 HTTP/3，它会在第一次 HTTP/2 响应的 Header 中夹带一条提示：
```http
Alt-Svc: h3=":443"; ma=86400

```


意思是：“我也支持走 UDP 443 端口的 HTTP/3，下次你可以直接连它。”
3. **无缝切换与自动兜底**：浏览器收到提示后，会在后台尝试建立 UDP QUIC 连接，后续请求直接切到 **HTTP/3**。如果用户所在的公司内网、校园网或运营商防火墙屏蔽/限速了 UDP 流量，浏览器会自动瞬间降级回 **HTTP/2**，用户完全无感知。

#### 2. YouTube 和 Bilibili 现在都在用 HTTP/3 吗？

**都在大规模使用，但两者的覆盖策略和侧重点略有不同：**

* **YouTube（几乎 100% 全量 HTTP/3）**
* HTTP/3 的前身 **QUIC 协议**本就是 Google 为了解决 YouTube 视频卡顿、首帧加载慢而发明的。
* 无论是网页端加载页面、调用 API 还是播放视频流，YouTube 的绝大部分流量默认全部走 `h3`（HTTP/3）。


* **Bilibili（核心视频流与移动端重度使用，Web 端混合使用）**
* B站的视频云团队（BVC）很早就深度投入了 QUIC 与 HTTP/3 的落地（甚至在 GitHub 开源了其自研的 `bilibili/nginx_quic_stack` 等组件）。
* **分布特点**：B站将 HTTP/3 重点部署在**视频分片分发（CDN 节点，如 `acgvideo.com`）和手机 App 端**。原因在于国内部分家庭宽带或运营商网络对大流量的 UDP 数据包存在 QoS 限速策略，因此 B站的调度系统会根据你当前的网络环境和运营商节点，动态决定视频流走 HTTP/3 还是回退到 HTTP/2；而网页端的常规列表、评论区等 API 接口则普遍使用已经足够快的 HTTP/2。

#### 3. 如何在浏览器里亲自验证？

你可以在打开 YouTube 或 B站播放视频时，通过以下步骤直接查看它们正在使用的协议：

1. 按下 **`F12`** 打开浏览器开发者工具，切换到 **Network（网络）** 面板。
2. 在请求列表的表头（如 `Name`、`Status` 那一行）点击**鼠标右键**，勾选 **Protocol（协议）** 列。
3. 刷新页面并播放视频，观察 `Protocol` 列的取值：
* **`h3`**：表示正在使用 **HTTP/3**（基于 UDP/QUIC）。
* **`h2`**：表示正在使用 **HTTP/2**（基于 TCP）。
* **`http/1.1`**：表示老旧的 **HTTP/1.1**。
